# Seed Data

What the local database holds before any real customer exists. For every table, three things:
**the migration that creates it**, **the seed module that fills it**, and **the rows**.

Not a plan — plans live in `docs/plans/`. This is the checklist the seed script is written against.

## Words used here

- **Migration** — one versioned SQL file that changes the *shape* of the database. Applied in order,
  they build the schema from empty.
- **up / down** — the two halves of a migration. `up` makes the change, `down` undoes it exactly.
  Drizzle Kit writes the `up`; the `down` is hand-written ([01 §5](plans/01-data-model-and-migrations.md)).
- **Upsert** — insert a row, or update it if a row with that id already exists. One statement.
  In Drizzle: `.onConflictDoUpdate()`.
- **Idempotent** — safe to run repeatedly. Ten seed runs leave the same rows as one.
- **Seed vs. data migration** — a seed fills a *local* database with fake fixtures and never runs in
  production. A data migration backfills *real* data and does, and lives in `api/drizzle/`.

**All money is integer cents.** `1800` is $18.00. No decimals anywhere in this file.

## File layout

```
api/
  src/db/schema.ts          every table definition, in one file
  drizzle/
    0000_catalog.sql        generated by `drizzle-kit generate --name=catalog`
    0000_catalog.down.sql   hand-written, undoes the above
    meta/                   Drizzle Kit's bookkeeping — never edit
  src/seed/
    ids.ts                  every stable UUID, one place
    catalog.ts              block 1
    users.ts                block 2
    orders.ts               block 3
    ops.ts                  block 4
    index.ts                opens the connection, runs blocks in order, closes
```

`npm run db:migrate` applies migrations. `npm run db:seed` runs `tsx src/seed/index.ts`.
Both are scripts in `api/package.json`, run explicitly — never on container start.

> [01 §5](plans/01-data-model-and-migrations.md) says the `down` sits beside the `up`. If Drizzle Kit
> ever objects to the extra file in that folder, move the downs to `api/drizzle/down/` keeping the
> same filename.

Every seed module exports one function, takes the database handle, and upserts by stable id so it is
idempotent. `index.ts` calls them in block order — a table can only be filled after the tables it
points at.

## Build blocks

Do a block at a time: write its tables into `schema.ts`, generate one migration for the block,
hand-write the `down`, apply, then write the seed module that fills it.

| Block | Migration | Seed module | Tables | Depends on |
| --- | --- | --- | --- | --- |
| 1 — Catalog | `0000_catalog` | `catalog.ts` | `shop_settings`, `suppliers`, `fabrics`, `fabric_price_history`, `silhouettes`, `hardware`, `features`, `shipping_zones` | nothing |
| 2 — Identity | `0001_identity` | `users.ts` | `users`, `measurement_profiles`, `measurement_flags` | 1 |
| 3 — Orders | `0002_orders` | `orders.ts` | `drops`, `saved_configurations`, `orders`, `order_features`, `order_hardware`, `order_events`, `sourcing_requests` | 1, 2 |
| 4 — Money & ops | `0003_ops` | `ops.ts` | `payments`, `processed_webhooks`, `order_messages`, `outbox`, `sourcing_candidates` | 3 |

**Block 1 is the whole first milestone.** It has no foreign keys pointing outside itself and it is
everything the configurator needs to price a garment. Stop there and check the site works before
starting block 2.

**Open question for block 3:** `orders.sourcing_request_id` and `sourcing_requests.order_id`
([01 §3](plans/01-data-model-and-migrations.md)) point at each other. One direction has to win, or
neither table can be inserted first. Resolve before generating `0002_orders`.

## `orders`

A slot is **occupied** at `SUBMITTED`, `QUOTED`, `DEPOSIT_PAID`, `IN_PRODUCTION` and **released** at
`READY`, `DECLINED`, `CANCELLED`, `EXPIRED`, `SLOT_FORFEITED` ([09](plans/09-capacity-slots-and-drops.md)).
The first five rows are what make the drop read 5/5.

([01 §4.2](plans/01-data-model-and-migrations.md)): `measurement_snapshot`, `yards_billed_at_quote`,

## Done when

Not "every table has rows" — that comes much later. In order:

- [ ] **Block 1** — the storefront shows open, closed, and full; the configurator prices a plain preset
- [ ] **Block 2** — two customers and an admin exist; `milo_flagged` raises all three warnings
- [ ] **Block 3** — the admin review screen has one submitted order; the portal shows every lifecycle state; the drop reads 5/5
- [ ] **Block 4** — the ops page shows a pending row, a dead-letter row, and two stale fabric prices
- [ ] `npm run db:seed` twice in a row leaves the database identical
